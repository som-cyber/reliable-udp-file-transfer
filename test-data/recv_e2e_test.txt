Product Requirements Document
Packetization and Packet Format (Week 2 Milestone)
Project: Reliable UDP File Transfer with Sliding Window
Module: UDP Communication & Packet Format
Module Owner: Somprakash
Milestone Scope: Week 2 — Packetization and Packet Format only
---
1. Overview
This PRD covers the second milestone of Somprakash's module: turning the raw send/receive from Week 1 into a real packet-based protocol — a defined header format, serialization, file chunking, sequence numbers, checksums, and receiver-side reconstruction. It builds directly on the Week 1 UDP sender/receiver and is a prerequisite for everything Abhipsa (reliability) and Sahil (sliding window) will do next.
2. Background
Week 1 proved that raw bytes can move between sender and receiver over UDP. That's not enough on its own: a real file transfer needs a way to split a file into pieces, label each piece so it can be identified and reassembled regardless of arrival order, and detect corruption. This milestone builds that packet layer.
3. Goals
Define a single, fixed packet format that sender and receiver — and eventually Abhipsa's and Sahil's modules — all agree on.
Split arbitrary files into chunks and wrap each chunk in a packet with a sequence number.
Detect corrupted packets via checksum.
Reconstruct the original file correctly on the receiver side, even if packets arrive out of order.
4. Scope
In scope (this milestone)
Finalizing the packet header format (type, sequence number, payload length, checksum, payload)
`packet.py` — packet structure, creation, serialization, deserialization
File chunking with a configurable chunk size
Sequence numbering of packets
Checksum generation and verification (`checksum.py`)
Receiver-side storage-by-sequence-number and file reconstruction (including out-of-order arrival)
Testing across different file sizes
Documenting the packet format, if needed, for the rest of the team
Out of scope (deferred)
Item	Where it belongs
ACK handling, timeout/RTO, retransmission	Abhipsa's module
Duplicate packet detection/handling	Week 3 — Reliability Integration Prep
Sliding window, Go-Back-N, Selective Repeat, flow control	Sahil's module
Real network loss/delay/reorder simulation, load testing, graphs	Protanu's module
Recovering from a detected corrupted packet (vs. just flagging it)	Abhipsa's module
5. Functional Requirements
ID	Requirement
FR-1	Finalize a fixed packet header: Packet Type, Sequence Number, Payload Length, Checksum, followed by the Payload.
FR-2	Implement `packet.py` with a `Packet` structure/class covering all header fields plus payload, and a way to construct one for a given chunk + sequence number.
FR-3	Implement `serialize(packet) -> bytes` and `deserialize(data) -> Packet`, using a documented fixed binary layout.
FR-4	Implement file chunking: split a file into fixed-size chunks (configurable size, e.g. 1024 bytes) to use as packet payloads.
FR-5	Assign an increasing sequence number (0, 1, 2, …) to each data packet, matching its chunk's position in the file.
FR-6	Implement `checksum.py`: generate a checksum over the payload when sending, and verify it on receipt, flagging each packet `VALID` or `CORRUPTED`.
FR-7	Implement receiver-side reconstruction: store each payload keyed by its sequence number as packets arrive (in any order), then concatenate in sequence order to rebuild the original file.
FR-8	Test the full pipeline (chunk → packet → serialize → send → receive → deserialize → reconstruct) across at least a few different file sizes.
FR-9	Document the packet format and serialization scheme, if needed, so Abhipsa and Sahil can build on it without guessing the byte layout.
6. Non-Functional Requirements
The binary packet format must be fixed and clearly documented — everyone on the team encodes/decodes it the same way.
Chunk size should be configurable, not hardcoded, since it affects both this module and Sahil's window sizing later.
`checksum.py` should be independently testable, separate from packet/serialization logic.
The packet `Packet Type` field should be designed to accommodate future values (e.g. `ACK`) even though only `DATA`/`START`/`END` are needed now.
No performance targets yet — correctness of packetization and reconstruction is the bar for this milestone, not speed.
7. Technical Stack (this milestone)
Python 3
`struct` — binary header packing/unpacking
`hashlib` — checksum generation/verification
`socket` — reused from Week 1 to actually send/receive the serialized packets
Git + GitHub for version control
8. Proposed Packet Format
```
+------------------+
| Packet Type      |   e.g. 1 byte  (DATA / START / END, extensible later)
+------------------+
| Sequence Number  |   e.g. 4 bytes (unsigned int)
+------------------+
| Payload Length   |   e.g. 2 bytes (unsigned short)
+------------------+
| Checksum         |   size depends on algorithm chosen (see Open Questions)
+------------------+
| Payload / Data   |   variable length, up to the configured chunk size
+------------------+
```
Exact field sizes and the checksum algorithm should be locked in as part of this milestone (see Open Questions) and then documented for the team.
9. Proposed Repository Additions
```
src/
├── udp_sender.py      (updated to build + send packets instead of raw bytes)
├── udp_receiver.py    (updated to receive + reconstruct via packets)
├── packet.py           (new)
├── checksum.py         (new)
└── file_utils.py       (new — chunking + reconstruction helpers)
```
10. Use Cases
As a developer, I can hand `file_utils.py` a file path and get back an ordered list of fixed-size chunks.
As a developer, I can wrap a chunk and its sequence number into a `Packet` and serialize it to bytes ready for `sendto()`.
As a developer, I can deserialize incoming bytes back into a `Packet`, check its checksum, and know immediately whether it's valid.
As a developer, I can feed the receiver packets in a shuffled order and still get back the exact original file.
11. Acceptance Criteria / Definition of Done
[ ] Packet format finalized and documented
[ ] `packet.py` implemented (structure, creation, serialize, deserialize)
[ ] Files can be split into chunks of a configurable size
[ ] Every data packet carries a correct sequence number
[ ] Checksum correctly flags valid vs. corrupted packets
[ ] Receiver stores packets by sequence number and reconstructs the file correctly, including out-of-order arrival
[ ] Tested against at least: a single-chunk file, a multi-chunk file, and a larger file
[ ] Packet format documented well enough for Abhipsa/Sahil to build on
[ ] Work committed to GitHub with message `feat: implement packet format and file packetization`
12. Test Plan
ID	Test	Expected Result
TC-1	Serialize a packet, then deserialize it	All fields match the original exactly
TC-2	Single-chunk file (smaller than one chunk size) round trip	Reconstructed file matches original byte-for-byte
TC-3	Multi-chunk file (several chunks) round trip	Reconstructed file matches original byte-for-byte
TC-4	Larger file (many chunks) round trip	Reconstructed file matches original; no missing/duplicated chunks
TC-5	Feed the receiver packets in shuffled (out-of-order) order	File still reconstructs correctly
TC-6	Deliberately corrupt one packet's payload before checksum verification	Checksum check correctly flags it `CORRUPTED`
13. Assumptions
Default chunk size is 1024 bytes unless the team agrees on a different value.
Sender/receiver from Week 1 are extended in place (not rewritten) to send/receive serialized packets instead of raw bytes.
"Out-of-order reconstruction" here means packets are simply stored and reordered by sequence number in a local test — it does not require simulating real network reordering (that's Protanu's territory).
A detected `CORRUPTED` packet is just flagged/logged at this stage; requesting a retransmission is Abhipsa's responsibility, not this milestone's.
Duplicate packets are not specifically tested here (that's called out as a Week 3 task in the plan).
14. Dependencies / Coordination
The packet format (especially `Packet Type` values and field sizes) should be shared with Abhipsa and Sahil once finalized, since their modules will read/extend it.
Chunk size choice affects Sahil's window-size planning, so it's worth flagging once decided.

This PRD covers only the **first milestone** of Somprakash's module: getting a minimal UDP sender and receiver working. It does **not** cover packet format, sequence numbers, checksums, or file chunking — those belong to Week 2 and later, and are intentionally out of scope here.

Before any of that can be built, there needs to be a working, agreed-upon way for two processes to exchange raw bytes over UDP. That's what this milestone delivers.

- Prove that a UDP sender and receiver can exchange data end-to-end.
- Establish the repo structure and environment conventions the rest of the module (and eventually the team) will build on.

# 2. Detailed Work Responsibilities

## 2.1 Somprakash --- UDP Communication and Packet Format

### Main Goal

Build the basic UDP communication layer and define how data will be
divided into packets, transmitted, received, checked, and reconstructed.

### Detailed Responsibilities

#### A. UDP Sender

-   Create a UDP socket.
-   Read the selected file from storage.
-   Divide the file into smaller chunks.
-   Create packets from those chunks.
-   Send packets to the receiver.
-   Track the packet sequence number.
-   Handle the end of file-transfer process.

#### B. UDP Receiver

-   Create a UDP socket and bind it to a port.
-   Receive UDP packets.
-   Extract packet information.
-   Pass received data to the reliability and reconstruction modules.
-   Save the received file to disk.

#### C. Packet Structure

Design a common packet format for communication between sender and
receiver.

A packet may contain:

``` text
+------------------+
| Packet Type      |
+------------------+
| Sequence Number  |
+------------------+
| Acknowledgement  |
+------------------+
| Payload Length   |
+------------------+
| Checksum         |
+------------------+
| Payload/Data     |
+------------------+
```

Possible packet types:

-   `DATA`
-   `ACK`
-   `START`
-   `END`
-   `FINISH`
-   `ERROR`

#### D. Sequence Numbers

-   Assign a unique sequence number to each data packet.
-   Use sequence numbers to identify missing packets.
-   Support detection of duplicate and out-of-order packets.

#### E. Serialization and Deserialization

-   Convert packet fields into bytes before transmission.
-   Convert received bytes back into packet fields.
-   Validate packet length and packet format.

#### F. Checksum

-   Calculate a checksum for packet contents.
-   Attach the checksum to each packet.
-   Recalculate and verify the checksum at the receiver.
-   Reject corrupted packets.

#### G. File Reconstruction

-   Store valid received packet data.
-   Arrange packet data in the correct order.
-   Reconstruct the original file.
-   Verify that the reconstructed file matches the original file.

### Expected Output

By the end of this module, the team should have:

-   A working UDP sender.
-   A working UDP receiver.
-   A documented packet format.
-   Packet serialization/deserialization functions.
-   Sequence-number handling.
-   Checksum verification.
-   Basic file reconstruction.

### Suggested Files

``` text
src/
├── udp_sender.py
├── udp_receiver.py
├── packet.py
```

## 2.2 Abhipsa --- Reliability Mechanism

### Main Goal

Make UDP file transfer reliable by detecting lost packets and requesting
or performing retransmission.

### Detailed Responsibilities

#### A. ACK Handling

-   Receive acknowledgements from the receiver.
-   Identify which packet has been acknowledged.
-   Maintain the acknowledgement status of packets.
-   Handle repeated or duplicate ACKs.

Example:

``` text
Sender                  Receiver

DATA 1  -------------------->
        <-------------------- ACK 1

DATA 2  -------------------->
        <-------------------- ACK 2
```

#### B. Packet-Loss Detection

-   Detect when an expected ACK is not received.
-   Identify missing packet sequence numbers.
-   Detect packet loss using timeout or acknowledgement information.

#### C. Timeout Mechanism

-   Start a timer after sending a packet or window.
-   Wait for the expected ACK.
-   Retransmit if the timer expires.
-   Stop the timer when the expected ACK arrives.

#### D. RTO Calculation

RTO means **Retransmission Timeout**.

The module will initially use a simple timeout value. If time permits,
it may estimate timeout using measured round-trip time.

The system should avoid:

-   Waiting forever for an ACK.
-   Retransmitting too quickly.
-   Sending unnecessary duplicate packets.

#### E. Retransmission

-   Retransmit lost packets.
-   Handle retransmission after timeout.
-   Keep track of the number of retransmissions.
-   Avoid losing already received data.

#### F. Duplicate Packet Handling

-   Detect packets that have already been received.
-   Avoid writing duplicate data into the output file.
-   Send an ACK again when necessary.

#### G. Out-of-Order Packet Handling

-   Detect packets that arrive before earlier packets.
-   Temporarily store out-of-order packets if required.
-   Deliver data to the file reconstruction module in the correct order.

#### H. Error Handling

Handle situations such as:

-   Invalid packet format.
-   Wrong checksum.
-   Missing ACK.
-   Duplicate ACK.
-   Unexpected packet sequence.
-   Receiver timeout.

### Expected Output

By the end of this module, the team should have:

-   ACK processing.
-   Timeout handling.
-   Packet-loss detection.
-   Retransmission logic.
-   Duplicate packet handling.
-   Out-of-order packet handling.
-   Retransmission statistics.

### Suggested Files

## 2.3 Sahil --- Sliding Window and Flow Control

### Main Goal

Improve transfer performance by allowing multiple packets to be in
transit instead of waiting for an ACK after every packet.

### Detailed Responsibilities

#### A. Sliding Window

Implement a sender window that controls how many packets can be sent
without receiving individual acknowledgements.

Example:

``` text
Window Size = 4

[1] [2] [3] [4]  → packets currently allowed to be sent
```

After ACK for packet 1:

``` text
[2] [3] [4] [5]
```

The window moves forward. This is why it is called a sliding window.

#### B. Sender Window Management

Maintain:

-   Base sequence number.
-   Next sequence number.
-   Window size.
-   Packets currently in transit.
-   Acknowledged packets.
-   Unacknowledged packets.

#### C. Receiver Window Management

Maintain:

-   Expected packet number.
-   Received packet buffer.
-   Out-of-order packets.
-   Acknowledgement status.
-   Delivery order.

#### D. Go-Back-N or Selective Repeat

The team will implement one main sliding-window retransmission strategy.

##### Go-Back-N

If one packet is lost, retransmit the lost packet and all later
unacknowledged packets.

Example:

``` text
Sent:       1  2  3  4  5
Received:   1  2     4  5

Packet 3 is lost.

Retransmit: 3  4  5
```

##### Selective Repeat

If one packet is lost, retransmit only the missing packet.

Example:

``` text
Sent:       1  2  3  4  5
Received:   1  2     4  5

Retransmit: 3 only
```

**Recommended implementation order:**

1.  Implement a basic sliding window.
2.  Implement Go-Back-N first because it is easier to debug.
3.  Add Selective Repeat only if the core system is stable and time is
    available.

#### E. Flow Control

-   Prevent the sender from overwhelming the receiver.
-   Limit the number of packets in transit.
-   Adjust sending according to the receiver window.
-   Avoid buffer overflow.

#### F. Transfer Synchronization

-   Coordinate the sender and receiver.
-   Handle start and end of transfer.
-   Ensure all required packets are acknowledged.
-   Confirm successful file completion.

### Expected Output

By the end of this module, the team should have:

-   Working sliding-window logic.
-   Sender and receiver window management.
-   Go-Back-N or Selective Repeat.
-   Flow-control mechanism.
-   Transfer completion synchronization.
-   Window-size configuration.

### Suggested Files

``` text
src/
```

# 6. Definition of Done

The project will be considered complete when:

-   The sender can read and split a file into packets.
-   The receiver can reconstruct the original file.
-   Packets contain sequence numbers and checksums.
-   ACKs are exchanged correctly.
-   Lost packets can be retransmitted.
-   Duplicate and out-of-order packets are handled.
-   Sliding-window transfer works.
-   Go-Back-N or Selective Repeat is implemented.
-   Packet loss, delay, and reordering can be simulated.
-   The system can measure latency, throughput, and retransmissions.
-   The team has generated graphs and analyzed the results.
-   The complete project is documented on GitHub.
-   All four members have contributed code, tests, documentation, or
    experiments.

# 7. Important Scope Control

To finish within eight weeks, the team should follow this implementation
order:

1.  Basic UDP file transfer.
2.  Packet format and checksum.
3.  Stop-and-Wait reliability.
4.  Sliding Window.
5.  Go-Back-N.
6.  Network emulator.
7.  Performance experiments.
8.  Optional Selective Repeat.

**Selective Repeat, advanced RTO estimation, packet duplication
simulation, and extra optimizations should be treated as optional
extensions.** The basic reliable UDP transfer with sliding window,
retransmission, checksum, and experiments should be completed first.
